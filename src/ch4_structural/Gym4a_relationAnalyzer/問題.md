## 1. 嚴重等級的設計問題（會導致編譯失敗或語意錯誤）

### Q1【嚴重】OOA 上 `RelationshipAnalyzer.parse` 兩個簽章只差回傳型別

**症狀**：
你在同一個介面同時列了：
- `parse(script: String): void`
- `parse(script: String): RelationGraph`

**為什麼錯**：
Java 語言規則明文禁止「**只用回傳型別重載**」。method signature 只看「方法名 + 參數型別清單」，回傳型別不算。所以這兩個 method 在 Java 編譯器眼中是**同一個 method 宣告了兩次** → 編譯不過。

更深層的設計問題：你誤以為基礎與進階兩版需求**共用同一個介面**，所以才把兩種 parse 硬塞進去。實際上 requirement 把它們寫在不同章節（A/B/C vs A2/B2），是**兩個獨立的介面契約**。

**建議怎麼改**：
1. **拆成兩張獨立的 OOA/OOD 圖**（一張畫基礎、一張畫進階）
2. 基礎版圖上的介面：
   - `<<interface>> RelationshipAnalyzer`
     - `+ parse(script: String): void`
     - `+ getMutualFriends(name1: String, name2: String): String[]`
3. 進階版圖上的介面：
   - `<<interface>> RelationshipAnalyzer`
     - `+ parse(script: String): RelationshipGraph`
   - `<<interface>> RelationshipGraph`
     - `+ hasConnection(name1: String, name2: String): boolean`
4. 兩張圖名字相同沒關係，反正不在同一個 package（`v1.RelationshipAnalyzer` 跟 `v2.RelationshipAnalyzer`）

**修正後示意（基礎版部分）**：
```
+----------------------------+
| <<interface>>              |
| RelationshipAnalyzer       |
+----------------------------+
| + parse(script): void      |
| + getMutualFriends(n1, n2) |
|     : String[]             |
+----------------------------+
```

### Q2【嚴重】OOD `RelationGraphAdapter` 不像 Adapter

**症狀**：
你畫的 `RelationGraphAdapter`：
- 實作 `RelationshipGraph` 介面
- 但只列了一個方法 `parse(script): RelationGraph`
- 沒有任何線連到「被 adapt 的第三方 Graph 套件」

**為什麼錯**：
1. **沒實作介面契約**：`RelationshipGraph` 介面的合約是 `hasConnection(...)`，Adapter 必須實作這個方法，不然根本通不過 `implements` 檢查。
2. **方法放錯類別**：`parse(script)` 是「**把腳本字串轉成 Graph**」的職責，這應該在 `RelationshipAnalyzer` 那邊（因為介面契約是 analyzer 提供 parse），不該長在 Adapter 上。
3. **沒看到 Adaptee**：Adapter 模式的精髓是「**把 Adaptee 包起來、用 Adapter 的介面對外**」。圖上沒畫被包的對象（第三方 Graph 套件）= 看不出 Adapter 模式。

**建議怎麼改**：
1. `RelationshipGraphAdapter` 的方法只留 **`hasConnection(name1, name2): boolean`**
2. 把 `parse` 方法移到一個新類別 **`RelationshipAnalyzerImpl implements RelationshipAnalyzer`** 上，由它負責讀腳本、建第三方 Graph、再 wrap 成 `RelationshipGraphAdapter` 回傳
3. `RelationshipGraphAdapter` 要畫一條**組合關係線（filled diamond 或 simple association with `1`）**指向 `ThirdPartyGraph`，並標一個欄位 `- adaptee: ThirdPartyGraph`
4. `RelationshipAnalyzerImpl` 跟 `RelationshipGraphAdapter` 之間是**「create」依賴**（dashed arrow with `<<create>>`）

**修正後示意（進階版核心結構）**：
```
RelationshipAnalyzer (介面)              RelationshipGraph (介面)
   △                                       △
   |                                       |
   |implements                             |implements
   |                                       |
RelationshipAnalyzerImpl  --create-->  RelationshipGraphAdapter
                                          |
                                          | ◆ 1 (組合)
                                          v
                                       ThirdPartyGraph (被 adapt 的對象)
```

### Q3【嚴重】`isMutualFriend` 回傳型別寫錯

**症狀**：
你畫：`isMutualFriend(targetName, name2, name3): String[]`

**為什麼錯**：
- requirement 第 60 行白紙黑字寫：「**回傳 true，代表是；回傳 false 代表不是**」 → 應為 `boolean`
- 你寫 `String[]` 完全違背了 SuperRelationshipAnalyzer 的對外合約
- 第二個參數應該是 `name1` 不是 `name2`（命名一致性）

**建議怎麼改**：
1. 把方法簽章改成 `+ isMutualFriend(targetName: String, name1: String, name2: String): boolean`
2. 注意這也影響了你寫 Adapter 時對它的呼叫方式：
   - **錯的呼叫方式**（你之前可能會這樣想）：`String[] result = super.isMutualFriend(...)`，然後 result 就是答案
   - **對的呼叫方式**：Adapter 必須**自己迭代所有候選名字**，逐一呼叫 `super.isMutualFriend(candidate, name1, name2)`，把回傳 `true` 的 candidate 收集起來成陣列
3. 因此 Adapter 內部必須在 `parse` 階段**自己記下「腳本中出現過哪些名字」**（變成一個 `Set<String> allNames` 欄位），讓 `getMutualFriends` 有迭代依據 → 這就是我 v1 code 裡 `RelationshipAnalyzerAdapter.collectNames()` 的用意

**修正後示意**：
```
SuperRelationshipAnalyzer
+ init(script: String): void
+ isMutualFriend(target: String, name1: String, name2: String): boolean
```

### Q6 OOD `Client` 不該揭露內部

**症狀**：
你的 OOD 中 `Client` 框畫了：
- `- script: String`（屬性）
- `+ load_script(filePath): String`（方法）

**為什麼錯**：
1. **違反「Client 不可修改」的硬約束**：題目明說 Client 是黑盒，OOD 不該揭露/新增它的內部結構。內部欄位是 Client 自己的事，不是你設計的範圍。
2. **資訊洩漏**：把別人的私有實作畫進你的設計圖，等於你在「規範別人怎麼寫」，越界了。
3. **命名違反 Java 慣例**：`load_script` 是 snake_case（Python 風），Java 慣例是 camelCase `loadScript`。

**建議怎麼改**：
1. OOD 圖上 `Client` 框**只標標題**（`Client` 或 `<<Client>>`），不畫屬性、不畫方法
2. Client 跟 `RelationshipAnalyzer` 之間的關聯線旁標明「**uses**」或「**1**」即可
3. 如果你真想表達「Client 從檔案讀腳本」，那放在 OOA 階段的便條紙（你已經放了，OK）就夠了，不該滲透進類別結構

## 4. 「JGraphT 是什麼」— 第三方 Graph 套件的概念解釋

> 這是回答你「第三方 Graph 要不要換真的 JGraphT？是什麼意思？」

### 4.1 requirement 說了什麼？
進階版 requirement 第 151 行：
> 「請你尋找一下你所使用的程式語言是否有第三方的 Graph 套件，能夠支援 connectivity analysis 等需求，並將其整合到程式碼之中。」

→ 意思是：**不要自己手刻一個 graph 資料結構**，去找一個現成、寫好的 Java graph 函式庫，把它 import 進來用。這就是「第三方套件」的意思。

### 4.2 JGraphT 是什麼？
**JGraphT** 是 Java 圈最知名的開源 graph 函式庫之一：
- Maven 座標：`org.jgrapht:jgrapht-core`
- 提供：`Graph<V, E>` 介面、`SimpleGraph`、`DirectedGraph` 等實作
- 內建演算法：BFS、DFS、Dijkstra、connectivity（連通性）、最小生成樹、最短路徑...
- 範例（如果用 JGraphT，code 大概長這樣）：
  ```java
  import org.jgrapht.Graph;
  import org.jgrapht.alg.connectivity.ConnectivityInspector;
  import org.jgrapht.graph.DefaultEdge;
  import org.jgrapht.graph.SimpleGraph;

  Graph<String, DefaultEdge> g = new SimpleGraph<>(DefaultEdge.class);
  g.addVertex("A");
  g.addVertex("B");
  g.addEdge("A", "B");

  ConnectivityInspector<String, DefaultEdge> inspector = new ConnectivityInspector<>(g);
  boolean connected = inspector.pathExists("A", "B");
  ```

### 4.3 我目前怎麼做？為什麼這麼做？
**目前**：我寫了一個 fake 的 `ThirdPartyGraph` 類別（`v2/ThirdPartyGraph.java`），它**模擬**了第三方套件會長的樣子（method 名為 `addPerson`、`link`、`pathExists` —— 故意跟 `hasConnection` 不同，這樣 Adapter 的「翻譯」工作才有意義）。

**為什麼不直接用 JGraphT**：
- 你這個 repo 沒有 Maven / Gradle build 系統（我看到的是 IntelliJ `.iml` + 純 javac）
- 加 JGraphT 需要：
  1. 建立 `pom.xml` 或 `build.gradle`
  2. 加 dependency `org.jgrapht:jgrapht-core:1.5.2`
  3. 整個 repo 改用 Maven/Gradle 編譯
  4. 可能要改 IntelliJ 專案結構

→ 對「練習 Adapter 模式」這個學習目標而言，**自寫 fake 第三方 vs 真的用 JGraphT，Adapter 模式長得一模一樣**，只差 Adapter 內部那一行呼叫（`adaptee.pathExists(...)` vs `inspector.pathExists(...)`）。教學上沒差別。

### 4.4 你要怎麼選？
| 選項 | 優點 | 缺點 | 建議情境 |
|------|------|------|----------|
| (A) 維持自寫 `ThirdPartyGraph`（我目前做的） | 不用建 build 系統、code 立刻跑得起來、Adapter 模式表達 100% 正確 | 嚴格說沒滿足「整合**真的**第三方套件」的字面意思 | **練習 Adapter 模式、寫作業交件** |
| (B) 換真的 JGraphT | 100% 滿足 requirement 字面、學到怎麼引入第三方 lib | 需要建 Maven/Gradle、整個 repo 結構要動 | **想練「整合 lib」這個技能、未來打算寫 production code** |

我的建議：**先用 (A) 完成練習**，等你想額外練習「在 Java 專案引入第三方套件」時，再請我把 v2 升級成 (B)。

## 5. 為什麼基礎與進階要拆成兩張圖？

> 這是回答你「為什麼需求不能放在一起寫成一張圖？」

### 5.1 短答
**技術上可以塞一張，但設計上會變成爛設計，而且很可能違反 SOLID 原則。**
你的 OOAD 衝突（特別是 Q1 的 parse 重載問題）就是「硬塞一張圖」直接造成的後果。

### 5.2 詳細理由

#### 理由 ① 兩個子題的 Adaptee（被適配對象）完全不同
- **基礎版（A/B/C）**：要 adapt 的是 `SuperRelationshipAnalyzer`（小華的類別）
- **進階版（A2/B2）**：要 adapt 的是**第三方 Graph 套件**（JGraphT 之類）
- 一個 Adapter 一次只 adapt 一個對象。如果硬要把兩個畫一起，等於這張圖在處理兩個無關的「翻譯任務」 → 違反 **SRP（單一職責原則）**

#### 理由 ② 介面契約不同
即使**名字都叫 `RelationshipAnalyzer`**，兩版的介面方法集是不同的：
| 章節 | parse 簽章 | 還有什麼方法 | client 怎麼用 |
|------|-----------|-------------|---------------|
| 基礎 | `parse(script): void` | `getMutualFriends(n1, n2): String[]` | `analyzer.parse(); analyzer.getMutualFriends(...)` |
| 進階 | `parse(script): RelationshipGraph` | （無——查詢都委託給 graph） | `graph = analyzer.parse(); graph.hasConnection(...)` |

**硬合在一起**會發生：
- 兩個 `parse` 簽章只差回傳型別 → Java 編譯不過（Q1 的根本原因）
- 介面變得肥大：同時有 `getMutualFriends` + `parse 回傳 Graph` → 違反 **ISP（介面隔離原則）**：客戶被迫依賴他用不到的 method

#### 理由 ③ Client 行為模式不同
- 基礎版 Client：`analyzer.parse(); print analyzer.getMutualFriends("A","B")`
- 進階版 Client：`graph = analyzer.parse(); print graph.hasConnection("A","B")`

進階版的 Client **跟 RelationshipGraph 也有依賴關係**（不只是跟 Analyzer）。基礎版完全不知道 Graph 存在。

→ 一張圖上畫兩個 Client、一個依賴 Graph、一個不依賴 → 圖會出現「**有些線只對某些 client 適用**」的尷尬狀況，無法清楚表達系統結構。

#### 理由 ④ 適配方向不同 → 設計理由不同
- 基礎版的設計理由：**小華的 API 不相容於 client 想要的介面，需要翻譯**
- 進階版的設計理由：**第三方套件的 API 跟我們對外承諾的介面不一樣，需要翻譯**

兩個都是 Adapter，但**動機與被適配方完全不同**。一張圖混兩個動機 = 看不出每個 Adapter 為什麼存在。

#### 理由 ⑤ 教學/思考的清晰度
**OOA / OOD 的本質是「我為什麼這樣設計」的視覺化**。
- 一張圖回答一個設計問題 → 讀者一眼看懂
- 一張圖混兩個獨立問題 → 讀者要先在腦中「拆開」兩個場景才能理解每個 Adapter 的存在意義 → 心智負擔翻倍

### 5.3 那如果硬要合一張會怎麼樣？

理論上可以：
- 把 RelationshipAnalyzer 設計成「同時有 `parse():void` 跟 `parse():RelationshipGraph`」（**Java 不允許**，要改名 `parseToGraph`）
- 或：兩個 Adapter 都同時實作（但這會讓單一 class 同時負責「適配 SuperXxx」和「適配第三方 Graph」，職責爆炸）

→ **每一條路都會引入新的設計缺陷**。所以正確答案是：**從一開始就拆兩張**。

## 10. 延伸筆記 A — `RelationshipAnalyzer` 為什麼必須是介面？

> 對話日期：2026-05-03。重點摘要。

### 10.1 是介面的三個獨立理由
1. **requirement 第 14 行明文要求**「先以介面來表達意圖」，且把「介面」與「具體實作類」分得很清楚（你 vs 小華的分工）
2. **Adapter 模式的 Target 必須抽象**：Adapter 是 Target 的眾多實作之一，Target 若是 concrete class 則 Adapter 失去意義
3. **DIP（依賴反轉原則）**：Client（high-level）跟 SuperRelationshipAnalyzer / 第三方套件（low-level）都應該依賴抽象，不該互相直接綁定

### 10.2 「不是 interface」的三種替代會崩在哪
| 替代方案 | 崩在哪 |
|---------|-------|
| 已有實作的 concrete class | Client 直接用就好，**Adapter 模式整個消失**，題目崩 |
| abstract class | Java 單繼承綁手綁腳，比 interface 嚴格更差，無實質好處 |
| 「不能修改」的 concrete class | 邏輯不通：寫死了又禁止改沒有意義 |

### 10.3 不是 Facade
| | Adapter（這題） | Facade |
|---|---------------|--------|
| 目的 | 翻譯不相容 API | 簡化複雜子系統 |
| Target 介面 | **事先存在** | **新發明的** |
| 包的對象 | 1 個（Adaptee） | 多個（整個子系統） |
| 客戶心聲 | 「介面不對，給我接一下」 | 「太複雜，給我簡化版入口」 |

### 10.4 為什麼 v1 沒有 Impl、v2 有？
**根本原因：Adapter 在不同位置。**

- **v1**：Adapter 適配的對象**正好是 Analyzer**（Target = `RelationshipAnalyzer`，Adaptee = `SuperRelationshipAnalyzer`）→ Adapter 同時兼任「Analyzer 的實作」，**不需要多一層**
- **v2**：Adapter 適配的對象**在 Graph 那邊**（Target = `RelationshipGraph`，Adaptee = `ThirdPartyGraph`）→ `RelationshipAnalyzer` 沒人 adapt，但介面總得有人實作 → 需要 `RelationshipAnalyzerImpl`（**普通實作，不是 Adapter**，可看成輕量級 Factory）

### 10.5 一句話總結
> `RelationshipAnalyzer` 是介面 = Adapter 模式 Target 必須抽象 + DIP 原則。
> v2 多一個 Impl 不是 Facade，是「介面總得有人實作」這件最樸素的事。
