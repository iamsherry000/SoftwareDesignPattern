## 0. TL;DR — 本題核心

**Proxy 模式雙重應用**：
- **PasswordProtectionProxy（Protection Proxy）** — 包 Database 介面，擋 RealDatabase 入口（B4）
- **VirtualEmployeeProxy（Virtual Proxy / Lazy Initialization）** — 包 Employee 介面，延遲載入下屬（B3）

**B1 不可修改、B3/B4 純擴充**：4 個 B1 元素（Database 介面、Employee 介面、RealDatabase、RealEmployee、Client）+ 2 個 B3/B4 擴充類別（兩個 Proxy）。

## 1. OOA / OOD 圖 vs requirement / code 對齊問題

### Q1【嚴重】OOD 圖 `PasswordProtectionProxy` 只列 `validPassword(): void`

**症狀**：圖上 `PasswordProtectionProxy` 框只列了一個 `+ validPassword(): void`，沒列 `getEmployeeById`。

**為什麼錯**：
1. **沒實作介面契約**：`PasswordProtectionProxy implements Database`，必須實作 `getEmployeeById`，否則編譯不過。
2. **可見度錯誤**：`validPassword` 是 Proxy 內部 helper（為了在 `getEmployeeById` 之前檢查密碼），應為 `private`，不該 public。
3. **回傳型別 void 沒語意**：「驗證密碼」結果只能 true/false 或 throw — void 無法傳遞 verify 失敗訊號。

**修正建議**：
- `+ getEmployeeById(id: int): Employee[0...1]`（必列，跟介面對齊）
- `- validPassword(): boolean`（私有 helper，回傳布林）
- 對應 code：見 `PasswordProtectionProxy.java`

---

### Q2【中等】OOA 圖 Employee 介面把 `subordinateIds 0..*` 標成 attribute

**症狀**：OOA 圖 Employee 介面欄位列了 `subordinateIds 0..*`，self-relation 連回 Employee。

**為什麼有點誤導**：
- requirement B3 範例 code 寫的是 `List<Employee> subordinates = employee.getSubordinates()`，**不是 `List<Integer> subIds`**。
- 介面方法應為 `getSubordinates(): List<Employee>`，不是 `getSubordinateIds(): List<Integer>`。
- `subordinateIds` 是 RealDatabase 從檔案讀出來的**內部資料**（純 Integer ID 列表），不該滲漏進 Employee 介面契約。

**code 怎麼處理**：
- `Employee.java` 介面只有 `getSubordinates(): List<Employee>`（對齊 requirement 範例 code）
- `subordinateIds: List<Integer>` 是 `VirtualEmployeeProxy` 內部欄位（lazy load 用）

OOA 圖的 `subordinateIds 0..*` 可以保留，但要理解為「**domain 知識**」（員工有 0..* 個下屬員工），不是介面方法。

---

### Q3【中等】OOD 圖 `VirtualEmployeeProxy → RealEmployee 0..1`

**症狀**：OOD 圖把 VirtualEmployeeProxy 跟 RealEmployee 用 0..1 association 連起來，暗示 Proxy 內部 wrap 一個 RealEmployee。

**設計選擇**：

兩種實作都符合需求 B3，差別在「lazy load 下屬後的 cache 形式」：

| 選項 | Proxy 內部欄位 | RealEmployee 何時 instantiate |
|---|---|---|
| **A — 嚴格照圖** | `realCache: RealEmployee`（lazy field）| 第一次 getSubordinates() 時建一個完整 RealEmployee（含 List<Employee>），之後委託給它 |
| **B — 精簡（我選的）** | `subordinatesCache: List<Employee>`（lazy field）| 從不 instantiate RealEmployee，Proxy 自己存 cache |

**我選 B**，理由：
- B 沒有重複資料（A 的 RealEmployee 會把 id/name/age 重複一份）
- B 更符合「Proxy 替代 RealSubject」的精神（外界永遠看 Proxy，不需要切換到 RealEmployee）
- 結果完全一樣（外部行為相同）

**RealEmployee 的角色**：在我的 code 中是「為 B1 設計圖保留的介面實作」，可作為「不需要 lazy 的 Employee」（例如未來測試用）。目前 system 中沒實際 instance — 但類別存在符合 B1 結構。

如果 Sherry 嚴格照圖要選 A，我可以改。

---

### Q4【中等】Lazy load 下屬時是否也過 Password Check？

**設計選擇**：

| 選項 | VirtualEmployeeProxy 持有的 Database | lazy load 是否過密碼 |
|---|---|---|
| **A — 嚴格照需求字面** | 外層 Database（PasswordProtectionProxy）| 過 |
| **B — 我選的** | RealDatabase（內層）| 不過 |

**需求 B4 字面**：「在存取 RealDatabase 的 getEmployeeId 操作時，必須在實際存取前先檢查 PASSWORD」 — 字面是「RealDatabase 所有 getEmployeeId 都要過」。

**我選 B 的理由**：
1. **設計意圖**：Password 是「擋外部 client 入口」的 Protection Proxy，內部 cascade 是同一個 client request 的延伸，不是新的 entry
2. **避免抽象污染**：A 方案要把外層 PasswordProtectionProxy 注入回 RealDatabase（self-reference），會讓 RealDatabase 知道 Proxy 存在，違背 Proxy 模式精神
3. **效能**：A 方案每個下屬載入都要做一次 env 檢查，重複 N 次

**code 實作**：`RealDatabase.parseEmployee` 內部 `new VirtualEmployeeProxy(..., this)` 直接傳 RealDatabase 自己。

如果 Sherry 嚴格照字面要選 A，要改 RealDatabase constructor 接受外層 Database 注入。

---

### Q5【輕】OOA 圖 Database 介面 `getEmployeeById` 回傳 `Employee[0...1]`

**對齊 ✓**：multiplicity `[0...1]` 對應 Java `Optional<Employee>`，符合「員工存在回傳資料、不存在用某種方式表達」需求。

## 2. requirement 沒明說、我作為架構師做的決策

| 決策項 | 我選的 | 理由 |
|---|---|---|
| Java package | `ch4_structural.Gym6b_employeeDb` | 對齊資料夾路徑（記取 Gym6a 教訓 — package 不對齊路徑會讓 IntelliJ/redhat.java 抓不到） |
| Database「員工不存在」表達 | `Optional<Employee>` | OOA 圖 `[0...1]` multiplicity 的標準 Java 對應 |
| Password 驗證失敗 | `throw IllegalStateException` | 「中斷存取」字面意思最明確；用 `Optional.empty()` 會跟「員工不存在」混淆 |
| RealDatabase 跳列邏輯 | `BufferedReader.readLine()` × `(id-1)` 次 + 讀第 id 列 | 符合 B2「跳到該員工所屬列讀那一筆」；不一次性 `readAllLines` |
| RealDatabase create 回傳什麼 | `VirtualEmployeeProxy`（不是 RealEmployee） | 為了支援 B3 lazy load — 如果直接 new RealEmployee 必須 eager load List<Employee>，跟 lazy 矛盾 |
| Lazy load 是否過 password | 不過（見 Q4） | Protection Proxy 是 entry 防護，cascade 不防 |
| Subordinate 載入失敗處理 | 跳過該下屬（用 `ifPresent`）| 員工資料表理論上 self-consistent，但安全起見 missing subordinate 跳過不爆 |
| Client 範例呼叫 | id=2, id=4, id=99 | id=2/4 有下屬可看 lazy load；id=99 不存在驗證錯誤路徑 |
| 測試資料 | requirement 範例的 6 筆 | 直接照需求文 |
