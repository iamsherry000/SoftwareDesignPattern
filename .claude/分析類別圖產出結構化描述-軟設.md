# 分析類別圖產出結構化描述

## 🎯 指令目的

在整理 Code Review 逐字稿之前，先將學員提交的 UML 類別圖（使用 Astah 繪製）轉換成結構化的文字描述（YAML 格式），以便後續的逐字稿整理和摘要產出能夠精準地使用正確的專有名詞。

---

## 📘 Context

### 為什麼需要這個步驟？

1. **圖片內容需要文字化**：AI 無法直接在後續步驟中重複讀取圖片
2. **逐字稿有錯字**：語音辨識會產生錯字（例如 Role → Raw），需要類別圖內容來修正
3. **課程特有元素**：這門課的類別圖包含特殊標記（Force、Resolved Force、便條紙），需要完整記錄

### 工具資訊

- **繪圖工具**：Astah
- **檔案格式**：PNG 或 JPEG
- **輸出格式**：YAML（搭配 JSON Schema 驗證）

---

## 🖼️ 圖片識別規則

### 需要分析的圖片

每個學員專案資料夾中通常包含三張圖：

1. `ooa_uml.png` 或 `ooa_uml.jpeg` - **OOA 類別圖**（領域模型）
2. `ood_uml.png` 或 `ood_uml.jpeg` - **OOD 類別圖**（設計藍圖）
3. `ood_sequence_diagram.png` 或 `ood_sequence_diagram.jpeg` - **序列圖**

⚠️ **注意**：學員可能會上傳錯誤（檔名與內容不符），你需要：
- 讀取三張圖片
- 自行判斷哪兩張是類別圖（Class Diagram）
- 識別哪張是 OOA（元素較少）、哪張是 OOD（元素較多，包含 Pattern）

## 📝 課程特有元素說明

### 1. 紅色箭頭 - Force（約束/衝突）

**定義**：來自 Christopher Alexander 的設計模式思維

- **概念**：Force 代表設計中的「約束」或「衝突」
- **作用**：Force 的存在定義了 Problem
- **解決**：Problem 存在才可以套用 Solution（設計模式）來解決

**在類別圖上的表現**：
- Astah 中用**紅色箭頭**標示
- 箭頭旁邊會有文字描述這個 Force 的內容
- 例如：「需要延遲載入以節省記憶體」、「需要保護敏感資料」

**在 YAML 中的記錄**：
```yaml
forces:
  - description: "需要延遲載入以節省記憶體"
    from: "Database"
    to: "Employee"
    color: "red"
```

### 2. 綠色箭頭 - Resolved Force（已解決的約束）

**定義**：已經被設計模式解決的 Force

- **概念**：原本的 Force 透過設計模式解決後，變成 Resolved Force
- **作用**：展示設計模式如何解決問題

**在類別圖上的表現**：
- Astah 中用**綠色箭頭**標示
- 箭頭旁邊會有文字描述解決方案
- 例如：「透過 Proxy Pattern 實現延遲載入」

**在 YAML 中的記錄**：
```yaml
resolved_forces:
  - description: "透過 Proxy Pattern 實現延遲載入"
    from: "EmployeeProxy"
    to: "RealEmployee"
    color: "green"
```

### 3. 便條紙 - 輔助說明（預設粉紅色）

**定義**：對類別的輔助描述

- **內容類型**：
  1. **行為描述**：說明某個方法的具體行為
  2. **職責說明**：說明類別的職責
  3. **常數說明**：列出類別使用的常數
  4. **其他輔助資訊**：任何需要額外說明的內容

**在類別圖上的表現**：
- Astah 預設是**粉紅色**便條紙
- 也可能是黃色或其他顏色
- 通常會用虛線連接到對應的類別

**在 YAML 中的記錄**：
```yaml
notes:
  - content: "負責管理所有員工資料，提供查詢和新增功能"
    attached_to: "EmployeeDatabase"
    color: "pink"
  - content: "execute() 方法會執行具體的攻擊邏輯"
    attached_to: "Action"
    color: "pink"
```

## 🔄 執行流程

### 步驟 1：讀取並識別圖片

1. 讀取指定資料夾中的三張圖片
2. 識別哪兩張是類別圖（排除 Sequence Diagram）
3. 判斷哪張是 OOA（元素較少）、哪張是 OOD（元素較多）

### 步驟 2：分析 OOA 類別圖

按照 YAML Schema 提取：
- ✅ 所有類別（Class）：名稱、屬性、方法
- ✅ 所有介面（Interface）
- ✅ 類別關係（繼承、實作、關聯等）
- ✅ 紅色箭頭（Force）
- ✅ 綠色箭頭（Resolved Force）- OOA 通常較少
- ✅ 便條紙（Notes）

輸出為 YAML 檔案：`ooa_analysis.yaml`

### 步驟 3：分析 OOD 類別圖

按照 YAML Schema 提取：
- ✅ 所有類別（Class）
- ✅ 所有介面（Interface）
- ✅ 類別關係
- ✅ 紅色箭頭（Force）- OOD 通常較少
- ✅ 綠色箭頭（Resolved Force）- OOD 較多
- ✅ 便條紙（Notes）
- ✅ **設計模式識別**（Patterns）- 重要！

輸出為 YAML 檔案：`ood_analysis.yaml`

### 步驟 4：儲存分析結果

將分析結果儲存到題目資料夾：
```
題目資料夾/
  ├── ooa_uml.png
  ├── ood_uml.png
  ├── ood_sequence_diagram.png
  ├── ooa_analysis.yaml  ← 新增
  └── ood_analysis.yaml  ← 新增
```

### ood_analysis.yaml

```yaml
diagram_type: "OOD"

classes:
  - name: "RealDatabase"
    methods:
      - name: "getEmployeeById"
        parameters: "id: String"
        return_type: "Employee"
        visibility: "+"

  - name: "RealDatabaseProxy"
    attributes:
      - name: "realDatabase"
        type: "RealDatabase"
        visibility: "-"
    methods:
      - name: "checkPassword"
        return_type: "boolean"
        visibility: "-"
      - name: "getEmployeeById"
        parameters: "id: String"
        return_type: "Employee"
        visibility: "+"

  - name: "EmployeeProxy"
    attributes:
      - name: "realEmployee"
        type: "RealEmployee"
        visibility: "-"
    methods:
      - name: "getSubordinates"
        return_type: "List<Employee>"
        visibility: "+"

  - name: "RealEmployee"
    attributes:
      - name: "id"
        type: "String"
        visibility: "-"
      - name: "subordinates"
        type: "List<Employee>"
        visibility: "-"
    methods:
      - name: "getSubordinates"
        return_type: "List<Employee>"
        visibility: "+"

interfaces:
  - name: "IEmployee"
    methods:
      - name: "getId"
        return_type: "String"
      - name: "getName"
        return_type: "String"
      - name: "getSubordinates"
        return_type: "List<Employee>"

relationships:
  - type: "realization"
    from: "EmployeeProxy"
    to: "IEmployee"
  - type: "realization"
    from: "RealEmployee"
    to: "IEmployee"
  - type: "composition"
    from: "EmployeeProxy"
    to: "RealEmployee"
    multiplicity_to: "1"
  - type: "dependency"
    from: "RealDatabaseProxy"
    to: "RealDatabase"

forces: []

resolved_forces:
  - description: "透過 Protection Proxy 解決密碼保護問題"
    from: "RealDatabaseProxy"
    to: "RealDatabase"
    color: "green"
  - description: "透過 Virtual Proxy 解決延遲載入問題"
    from: "EmployeeProxy"
    to: "RealEmployee"
    color: "green"

notes:
  - content: "Proxy Pattern - 保護代理"
    attached_to: "RealDatabaseProxy"
    color: "pink"
  - content: "Proxy Pattern - 虛擬代理"
    attached_to: "EmployeeProxy"
    color: "pink"

patterns:
  - name: "Proxy"
    participants:
      - "RealDatabaseProxy"
      - "RealDatabase"
  - name: "Proxy"
    participants:
      - "EmployeeProxy"
      - "RealEmployee"
      - "IEmployee"
```

## 💬 使用方式

```
@分析類別圖產出結構化描述.md [題目資料夾路徑]
```

例如：
```
@分析類別圖產出結構化描述.md "code-review-2025-10-17/01 2219 6.B 【延遲載入】員工資料表存取 ★"
```

---

## ⚠️ 注意事項

1. **精準度優先**：類別名稱、方法名稱必須與圖片完全一致，包括大小寫
2. **Force 是重點**：紅色和綠色箭頭是這門課的核心，務必完整記錄
3. **便條紙很重要**：便條紙通常包含關鍵的設計意圖說明
4. **Pattern 識別**：OOD 中要識別出使用了哪些設計模式
5. **不要遺漏**：寧可多記錄，也不要遺漏任何元素
